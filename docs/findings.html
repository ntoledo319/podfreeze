What 83 real Podfile.lock files say about the CocoaPods trunk freeze

Measured on 15 September 2026 against public iOS repositories. Every number here came from running a scanner over real files, not from an estimate.

On 2 December 2026 CocoaPods trunk stops accepting new podspecs (announcement). Builds keep working. What ends is the ability of a pod to publish another version on the coordinate you depend on — including a fix for a vulnerability discovered in 2027.

The obvious question is how much that actually affects real projects. So I measured it.

The headline number

96%

of projects whose dependency sources can be determined have at least one pod that can never receive another published version after the freeze.

29% of the projects in this corpus depend on Firebase — and that matters more than the December date, because Firebase stops publishing new versions to CocoaPods in October 2026, two months earlier. For roughly a third of these projects, the real deadline is not the one in the headlines.

It is worth saying plainly what the Firebase data already shows: FirebaseAuth's most recent publish to trunk was September 2022. Firebase effectively left CocoaPods years ago. If you are still installing it through CocoaPods, you have been running on a frozen version for some time without anything telling you.

A quarter of lockfiles cannot answer the question at all

26 of 83 lockfiles — 31% — were written by CocoaPods versions predating the SPEC REPOS section, so the file simply does not record where each pod came from. The oldest in the corpus was written by CocoaPods 0.33.1.

For those, the honest answer is "unknown", and any tool that reports them as clean is guessing. Re-running pod install with a current CocoaPods rewrites the lockfile with source information and makes the question answerable.

Method. Lockfiles were collected via the GitHub code search API across five different queries (SPEC REPOS, Firebase, EXTERNAL SOURCES, React-Core, CHECKOUT OPTIONS) to avoid sampling one shape of file, deduplicated by repository, and scanned with podfreeze v0.5.1. A pod counts as exposed when the lockfile lists it under the central specs index under any of its spellings (trunk, https://github.com/CocoaPods/Specs, with or without .git). Pods pinned via EXTERNAL SOURCES or resolving from a private spec repo are counted as insulated. Counts were verified against the raw files by an independent script, not by the scanner alone.
What this sample is not. GitHub code search does not return a random sample of iOS projects. It skews toward smaller, older, public repositories — the kind that get indexed — and away from large commercial apps, which are mostly private. Treat 96% as "nearly every project in this corpus", not as a population estimate for the App Store. The direction is solid; the exact figure is not transferable. 83 is also a small sample: it is what could be collected and hand-verified in one sitting, and it is stated rather than rounded up.
